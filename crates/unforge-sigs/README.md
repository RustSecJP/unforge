# unforge-sigs

ストリップされた Rust バイナリの関数に、指紋（fingerprint）で名前を付け直すためのクレートです。IDA の FLIRT や Ghidra の Function ID と同じ考え方です。

マルウェアはふつうストリップされていますが、unforge-analysis はソースパスから、中に入っているクレートとその版、ツールチェーン（rustc のコミット）を読み取れます。そのコードは公開されているので、シンボルが残っている別のバイナリから指紋のデータベースを作っておけば、ストリップされたバイナリの関数を引き当てられます。

```sh
unforge sig build -o std.db path/to/with-symbols-1 path/to/with-symbols-2
unforge sig build -o all.db std.db other.db          # データベースどうしをまとめる
unforge sig match --db all.db path/to/stripped
```

GitHub Actions で、Rust の版ごとの標準ライブラリと、よく使われる crate のデータベースを作っています。落とし方と使い方は [sigs/README.md](../../sigs/README.md) を見てください。

## 指紋

関数を、その大きさいっぱいに unforge-disasm で逆アセンブルし、末尾の詰め物（`nop`、`int3`）を除き、命令ごとに「ニーモニック + オペランド（Intel 記法）」の一行にします。そのとき、リンクしたときの配置で変わる数だけを置き換えます。

| オペランドの中の数 | 置き換え | 理由 |
|---|---|---|
| 関数の中を指す分岐先 | `L<関数の先頭からの差>` | 関数自身のコードだけで決まるので残す |
| 関数の外を指す分岐先・呼び出し先 | `T` | 呼ばれる側の位置は別のバイナリでは違う |
| RIP 相対で指すアドレス | `T` | データや GOT の位置は配置で変わる |
| `fs:[..]` / `gs:[..]` の 0 以外の変位 | `F` | TLS の配置はリンクされたスレッドローカル全体で決まる |
| `ebx` からの変位（`[ebx+0xe8]`） | `G` | i386 の PIC は GOT のアドレスを `ebx` に置き、データを GOT からの差で指す |
| 64 ビットのコードで、同じファイルの `PT_LOAD` に入る 0x1000 以上の数 | `A` | 非 PIE のコードの絶対アドレス |
| 32 ビットのコードで、0x1000 以上 0xffff0000 未満の数 | `A` | i386 の PIC の GOT からの差（`add ebx, 0x6dde6`）は定数と見分けられない |
| それ以外（即値、スタックやフィールドの変位、スケール） | そのまま | ソースとコンパイラで決まり、関数の中身を表す |

レジスタ名、ニーモニックと接頭辞（`lock cmpxchg`）、メモリオペランドの大きさと形（`qword ptr [rax+rcx*8+0x10]`）もそのまま残します。

ハッシュは FNV-1a 64 で、各行（後ろに `\n`）と命令数（u32 リトルエンディアン）にかけます。バイト単位で定義されていて、プラットフォームにも Rust の版にも左右されません。命令数とバイト数もハッシュと一緒に持ちます。

## 小さい関数

`mov eax, 1; ret` のような短い関数は、関係のない多くの名前で同じコードになります。既定では 6 命令未満か 16 バイト未満の関数を、作るときも引き当てるときも飛ばします（`--min-insns`、`--min-bytes` で変えられます）。

## 衝突

同じ指紋に複数の名前が付くことがあります（型を変えて実体化したジェネリック関数や、本体が同じ別の関数）。データベースは名前を全部（16 個まで）持ち、引き当ての結果は次のどれかです。

- `unique`: 名前が一つ。
- `generic`: どれも同じジェネリック関数の実体化（`core::ptr::drop_in_place<..>  [generic: 3]`）。
- `ambiguous`: 関係のない名前が並ぶ。最初の名前を表示し、`[ambiguous: N]` を付けます。

## 関数の開始位置

このブランチの `Analysis::functions` は、まだ `.eh_frame` を読みません（別のブランチで追加中）。そこで引き当てでは、`Analysis::functions` の関数（シンボル、動的シンボル、エントリポイント）に加えて、`.eh_frame_hdr` の探索表にある開始位置と、そこから逆アセンブルして見つけた直接の呼び出し先・関数の外へのジャンプ先も使います。大きさの分からない関数は、次の開始位置までとします（末尾の詰め物は指紋から除くので、ずれません）。

## データベースの形式

版付きのバイナリ形式です。どの一覧も整列して重複がなく、同じ入力からは必ず同じバイト列になります（`Db::from_bytes(b)?.to_bytes() == b`）。詳しくは `src/db.rs` の説明を見てください。

大きさは、リリースビルドのコードで指紋 1 万件あたり約 1.0 MB（名前一つあたり約 95 バイト）、デバッグビルドでは名前の付いた関数 1 万件あたり約 1.7 MB です。84〜95 % は名前の文字列です。

## 評価

`examples/score.rs` で測りました（rustc 1.99.0 `b940084d7`、x86-64）。A（シンボルあり）からデータベースを作り、B を `strip --strip-all` したものを引き当て、B 自身のシンボルと同じアドレスで比べます。

- 正解: `unique` は B の名前と同じとき、`generic` は B の名前が同じジェネリック関数の実体化のとき。`ambiguous` は名前を付けたうちに数えません。
- 精度（P） = 正解 / (`unique` + `generic`)
- 再現率（R） = 正解 / B の関数のうち A にも同じ名前があるもの（しきい値を使うときは、それを超えるもの）

`collections` などは `testdata/src/*.rs` を `x86_64-unknown-linux-musl`（静的 PIE、std と musl 入り）でビルドしたものです。「i686」の行は `i686-unknown-linux-musl` です。下の 3 行は、このワークスペースのデバッグビルドの実行ファイル（`unforge-bench` とその単体テスト、`unforge` とその単体テスト）です。

| A → B | 既定（6 命令 / 16 バイト） | しきい値なし |
|---|---|---|
| collections → collections（同じファイル） | P 100.0 %、R 87.0 %、ambiguous 35 | P 100.0 %、R 78.9 %、ambiguous 101 |
| collections → enums（opt 3） | P 100.0 %、R 86.0 %、ambiguous 39 | P 100.0 %、R 77.7 %、ambiguous 108 |
| collections → traits（opt 3） | P 100.0 %、R 86.2 % | P 100.0 %、R 77.6 % |
| collections → panics（opt 3） | P 99.8 %、R 86.5 % | P 99.8 %、R 78.3 % |
| collections → ffi_statics（opt 3） | P 99.5 %、R 86.2 % | P 99.1 %、R 77.9 % |
| collections → enums（どちらも opt 0） | P 99.0 %、R 86.5 % | P 98.9 %、R 78.0 % |
| collections opt 3 → enums opt 0 | P 100.0 %、R 85.4 % | P 99.7 %、R 76.9 % |
| ほか 4 本 → traits（opt 3） | P 99.5 %、R 86.7 % | P 99.5 %、R 77.9 % |
| unforge-bench → その単体テスト（デバッグ） | P 95.7 %、R 78.4 % | P 95.8 %、R 68.0 % |
| unforge → その単体テスト（デバッグ） | P 94.6 %、R 82.6 % | P 94.3 %、R 73.5 % |
| unforge-bench → unforge（デバッグ） | P 88.8 %、R 85.5 % | P 88.8 %、R 72.0 % |
| i686: collections → collections | P 100.0 %、R 88.8 % | P 100.0 %、R 85.7 % |
| i686: collections → enums（opt 3） | P 100.0 %、R 81.1 % | P 100.0 %、R 78.2 % |

`cargo test -p unforge-sigs` は、std だけの小さなプログラム二つを `rustc -O`（x86_64-unknown-linux-gnu、glibc に動的リンク）でビルドして同じことを確かめます。手元では既定で P 99.8 %、R 91.9 %、しきい値なしで P 99.8 %、R 82.6 % でした。

分かったこと:

- 再現率を下げているのは正規化ではありません。両方にある同じ名前の関数は、ほぼ必ず同じ指紋になります（`--diff` で見ると、違うのは組み合わせごとに 1〜2 件で、インライン展開が違ったもの）。取りこぼしは、同じコードに別の名前があるもの（`ambiguous`）と、musl のバイナリでアンワインド情報を持たず関数ポインタからしか呼ばれない C ライブラリの関数（開始位置が見つからない）です。
- 間違いは、別の名前で同じコードになるものです（`<u32 as Debug>::fmt` と `<usize as Debug>::fmt`、データベースにない型で実体化されたジェネリック関数）。デバッグビルドでは小さなジェネリック関数がすべて別の関数として残るので、精度が下がります。マルウェアはふつうリリースビルドです。
- しきい値は精度をほとんど変えませんが、`ambiguous` を 3 分の 1 に減らします。しきい値なしだと、正しく名前が付く関数の数は 6 % ほど増えますが、`ambiguous` が 3 倍になります。

## 制約

- 標準ライブラリの指紋は、rustc のコミットごとに作る必要があります。std は rustc と一緒にビルド済みで配られるので、同じ版ならどのバイナリでも同じコードになりますが、版が変わればコードも変わります。`sig match` は、対象のバイナリの依存（rustc のコミットを含む）のうちデータベースの元に入っていないものを表示します。
- ジェネリック関数や `#[inline]` の関数は、使う側のクレートで、その最適化レベルでコンパイルされます。データベースに入れるバイナリと最適化レベルが違うと、そうした関数は一致しにくくなります。
- 32 ビットの PIC コードで、`ebx` 以外のレジスタに置いた GOT からの 0x1000 未満の差は見分けられません（データの流れを追う必要があります）。i686 で別のバイナリへの再現率が x86-64 より低いのはこのためです。x86 / x86-64 以外の CPU には対応していません。
- 指紋は呼び出し先や参照する文字列を見ないので、それだけが違う関数（`core::cell::panic_already_borrowed` と `panic_already_mutably_borrowed` など）は区別できません。
